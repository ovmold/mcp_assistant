# AGENTS.md

## Назначение проекта

MCP-ассистент инженера поддержки на Python, GigaChat и Model Context Protocol. Агент ищет тикеты в SQLite, работает со статьями базы знаний в Markdown, добавляет комментарии и меняет статусы после подтверждения пользователя.

## Структура

- `src/mcp_assistant/client/` — приложение агента: агентный цикл, LLM- и MCP-клиенты, подтверждения, трассировка, системный промпт и UI.
- `src/mcp_assistant/client/main.py` — точка входа CLI/Gradio.
- `src/mcp_assistant/client/agent_prompts.py` — системный промпт агента.
- `src/mcp_assistant/client/servers.json` — MCP-серверы, лимиты и таймауты.
- `src/mcp_assistant/servers/` — MCP-инструменты тикетов и базы знаний.
- `src/mcp_assistant/storage/` — модели данных, SQL-схема и общие функции timestamps.
- `src/mcp_assistant/config.py` — общие пути и настройки окружения.
- `src/mcp_assistant/seed.py`, `seed_data.py` — создание тестовых данных.
- `tests/` — unit- и интеграционные тесты.
- `evals/` — сценарии оценки агента.

Сохранять границы `client/`, `servers/` и `storage/`: не переносить клиентскую логику в серверы или утилиты сидирования. Не возвращать общую папку `scripts/` для несвязанных модулей.

## Среда и команды

Проект использует Python 3.12+ и `uv`. Команды выполняются из корня репозитория.

Установка зависимостей:

```bash
uv sync
```

Создание тестовых данных:

```bash
uv run python -m mcp_assistant.seed
```

Seed при каждом запуске полностью пересоздаёт БД и базу знаний, включая удаление дополнительных Markdown-файлов. Не запускать без явного запроса пользователя.

Запуск MCP-сервера базы знаний в отдельном терминале:

```bash
uv run python -m mcp_assistant.servers.knowledge
```

Запуск агента:

```bash
uv run python -m mcp_assistant.client.main --ui cli
uv run python -m mcp_assistant.client.main --ui gradio
```

Проверка всех тестов:

```bash
uv run pytest -q
```

Проверка сборки:

```bash
uv build
```

Удалять созданный проверкой каталог `dist/`, если артефакты сборки не нужны пользователю.

## Правила изменений

- После изменения кода запускать относящиеся к нему тесты, а перед завершением — весь `pytest`.
- При изменении структуры, импортов или команд обновлять README, evals и тесты, которые используют соответствующие пути.
- При изменении схемы БД сохранять синхронизацию FTS5 через триггеры и нормализацию регистра и ё/е в индексе и запросе; проверять `tests/test_tickets.py` и `tests/test_mcp_layer.py`.
- SQL-параметры передавать через placeholders, не через форматирование пользовательских значений.
- Имена статей базы знаний валидировать; нельзя разрешать обход `KB_DIR` через path traversal. Модель эмбеддингов и статьи должны инициализироваться до запуска MCP-сервера knowledge. Поиск использует BM25 и эмбеддинги; точные лексические совпадения должны иметь приоритет над чисто семантическим сходством.
- Инструменты записи должны требовать подтверждения через MCP-аннотации и/или `always_confirm_by_server`. В `add_comment` аргумент `author` обязателен; если он неизвестен, агент сначала спрашивает пользователя. В `update_status` переход `closed → open` и вызов с неизменным статусом запрещены.
- Параллельно через GigaChat SDK 0.2.4 выполнять только независимые read-only вызовы; сохранять ID вызовов и `tools_state_id` в истории, а запись и подтверждения выполнять последовательно. Отказ пользователя должен останавливать текущий `run()` и все оставшиеся вызовы.
- После исчерпания `max_steps` выполнять только один финальный запрос без инструментов для частичного ответа; при его ошибке возвращать сообщение о лимите.
- MCPClient должен получать и поддерживать инструменты, ресурсы, шаблоны ресурсов и промпты. Сообщения MCP-промптов добавлять в историю с исходными ролями, а результаты ресурсов и функций сопоставлять по ID и `tools_state_id`.
- Сохранять изоляцию историй по `session_id`, очистку неактивных сессий и корректное завершение фоновых задач Gradio.
- Закрывать GigaChat, MCP-подключения и `Tracer` на всех путях завершения, включая ошибки инициализации. Не запускать агент с частично подключёнными MCP-серверами; `ExceptionGroup` разворачивать до исходных причин.
- `conf.load_env()` должен выполняться до использования путей из окружения; после загрузки пути пересчитываются автоматически.
- Не читать, выводить или копировать секреты из `.env`. Для документации использовать `.env.example`.
- В stdio MCP-серверы передавать `get_default_environment()` и только явно заданные переменные; не наследовать полный `os.environ`.
- Не добавлять зависимости без необходимости; сначала проверять `pyproject.toml` и существующие импорты.
- Комментарии добавлять только к неочевидной логике и обновлять их при изменении поведения.
- Ошибки основного LLM-вызова записывать как `llm_error`; MCP `isError` сохранять в `tool_result.is_error`, а исключения инструментов — в `tool_error`.

## Тесты и evals

Тесты используют `pytest`, `pytest-asyncio`/AnyIO и временные каталоги. Для тестов БД и базы знаний использовать существующие фикстуры `temp_db` и `temp_kb`, не изменять реальные файлы в `data/`.

Для запуска evals сначала нужен сервер базы знаний:

```bash
uv run python evals/run_evals.py
```

Evals могут обращаться к GigaChat и изменять тестовые данные; запускать их только когда это требуется задаче.
